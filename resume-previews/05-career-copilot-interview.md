# Career Copilot：面试解释与参数手册

这份说明对应 `01-ai-agent-engineering-detailed.md`、`02-ai-product-detailed.md` 和 `03-ai-solution-detailed.md` 中的 Career Copilot 项目。回答时先说边界：这是一个“岗位发现—证据检索—排序—简历草稿—人工审批”的系统，不是无人值守的自动投递器。

## 30 秒版本

我把求职流程拆成可审计的 Agent 工作流。岗位先经过规则过滤，再用已核验 Career Vault 证据计算语义匹配，最后叠加同渠道历史反馈；生成简历时只选择已核验证据，并附上岗位和证据引用。MCP 工具按读、草稿、需审批写入分层，真正的申请状态变更和邮件发送必须经过人工确认。向量服务不可用时系统明确切换到 lexical 模式，而不是假装完成了向量检索。

## 一次请求怎么走

1. 读取岗位、用户偏好、已核验项目证据和历史申请状态。
2. `calculateRuleScore` 检查实习性质、学生/毕业年份、地点、每周天数、最短月份、截止日期和来源可靠性。
3. `calculateSemanticScore` 将岗位描述与证据的技能、项目名、证据文本做 token 交集，形成语义近似分。
4. `calculateHistoryScore` 从同渠道的已提交、已读、沟通、面试和 offer 状态计算反馈分。
5. `rankJobHybrid` 组合三类分数，输出等级、阻塞原因、缺失技能、解释和引用。
6. `generateResumeDraft` 按岗位 token、persona 优先技能和证据置信度选最多 6 条证据，生成对应方向的草稿。
7. `evaluateGrounding` 检查输出长度、引用覆盖和引用类型；不通过就保留为待修订草稿。

## 岗位排序参数：调什么、影响什么

| 参数/规则 | 当前实现 | 调大或放宽的效果 | 调小或收紧的效果 |
|---|---|---|---|
| 规则/语义/历史权重 | `0.4 / 0.4 / 0.2` | 提高某一项会让该信号更能改变总分；语义权重高会偏向项目技术匹配 | 权重降低后该信号影响变弱；历史样本少时不应盲目提高历史权重 |
| 规则分中的岗位方向 | 命中 AI Agent、AI 产品、解决方案、全栈等方向加 18，否则加 8 | 扩大方向词表会提高召回，可能带来更多误匹配 | 收紧词表能压制标题党岗位，但会漏掉描述写得不标准的岗位 |
| 技能分 | 命中技能数 / JD 技能数，最多 28 分 | 增加技能证据覆盖会提高分数和可解释性 | 只保留强相关技能可减少“关键词堆砌”造成的假阳性 |
| 地点/远程 | 命中优先地点加 16，否则加 7 | 扩大地点白名单能提高远程或跨城召回 | 收紧白名单能压制不接受的线下地点 |
| 学生与 2028 届硬条件 | `accepts_students=true` 加 8，`accepts_2028=true` 加 10；明确为 false 直接阻塞 | 将未知值视为待确认，而不是直接通过 | 把未知值按不通过处理会更安全，但会降低待复核数量 |
| 每周天数/月份 | 未填写或 `days_per_week >= 3` 加 6；未填写或 `minimum_months >= 3` 加 6；低于规则进入 blocker | 放宽阈值会增加候选；只有在用户明确接受时才应放宽 | 收紧阈值会更有效抑制时间冲突 |
| 来源可靠性 | `source_reliability(1..5) * 2`，再限制到 2..10 | 提高可靠来源权重，让官方/可回溯来源靠前 | 降低该权重可避免来源分数掩盖内容不匹配 |
| 阻塞上限 | 只要有 blocker，规则分和最终分都不超过 49 | 不应通过调大权重绕过 blocker | 这是抑制误投的硬闸门，不能为了好看删除 |
| 等级阈值 | S≥85，A≥75，B≥60，否则 C | 降低阈值会扩大 S/A 推荐集 | 提高阈值会减少推荐但提高精度；阈值变化必须配合历史回测 |

最终分实际是：`rule * 0.4 + semantic * 0.4 + history * 0.2`。没有历史样本时历史分固定为 50，是中性基线，不代表岗位已经验证有效。

## 语义、证据和检索参数

- 单条证据的语义分：`skillScore * 0.8 + lexicalScore * 0.2`。技能命中比普通文本重合更重要；提高 0.8 会增强技能精度，降低它会增强对自然语言描述的召回。
- 词法分的分母被限制在 `max(6, min(jobTokens, 30))`，避免短 JD 造成单词命中就满分，也避免超长 JD 把分数稀释到没有意义。
- 语义证据最多取前 5 条，聚合为 `best * 0.75 + supporting_average * 0.25`。提高 0.75 会更相信最强证据；提高 supporting 权重会抑制单条偶然命中，要求多条证据一致。
- 简历证据最多选 6 条，选择分是：`岗位 token 命中 * 3 + persona 技能命中 * 2 + confidence / 100`。提高岗位命中系数会让简历更贴 JD；提高 persona 系数会让同一套简历更稳定地保持方向；提高 confidence 的影响会更偏向人工核验过的强证据。
- Career Vault 证据必须 `active != false` 且 `verification_status=verified`。未核验材料不能自动升级为简历事实。
- 向量/embedding 不可用时走 lexical 模式；结果会标明 `mode=lexical`，不能在面试中说成“向量召回仍然正常”。

## 如何保证确定性

确定性分三层回答：

1. **排序确定性**：同一份岗位、证据、历史数据和同一版本 `hybrid-v1` 公式，规则分、语义分、历史分和等级可重复；同分时按岗位标题排序。
2. **证据确定性**：证据带有 id、来源、置信度和引用；生成契约要求“只保留事实、只用已核验证据、只在有支持时量化、不虚构公司或指标”。
3. **模型边界**：外部 LLM 的采样并没有被系统声称为完全确定；Grounding 检查只能保证引用和输入约束，不能把概率模型变成数学上的固定输出。若面试官追问 temperature/seed，应诚实说：当前排序和本地规则路径是确定的，外部模型的 `temperature/seed` 只有在具体供应商支持且显式配置时才会纳入复现控制。

## 服务不可用时怎么办

| 故障 | 系统动作 | 不能做什么 |
|---|---|---|
| embedding API 无 key/超时 | 使用 lexical 排序，保留检索模式和状态 | 不能声称完成了向量检索 |
| Supabase/数据库短暂不可用 | API 返回错误或队列保持待处理，稍后由 Scheduler 消费 | 不能把空结果写成成功，也不能伪造申请状态 |
| 队列任务尚未完成 | 返回 job id，客户端轮询 `queue_jobs/queue_results`；claim/complete/fail 状态分离 | 不能同步等待长任务后假装已完成 |
| 外部岗位源不可达 | 记录来源健康和重试时间；发现结果仍需回溯 | 不能把旧缓存包装成今天的新岗位 |
| grounding 不通过 | 保留草稿、显示缺失引用或不允许的引用类型，要求修订 | 不能直接发送邮件或改申请状态 |
| MCP 写工具 | `create_email_draft`、`update_application_status` 标记为 approval_required | 不能无人值守投递；当前运行时也明确 `automaticSubmission=false`、`automaticEmailSend=false` |

## 高频追问与回答

**为什么权重是 0.4/0.4/0.2？**

这是一个可解释的初始策略：规则和项目语义各占 40%，历史反馈占 20%，避免小样本历史把当前匹配完全覆盖。上线后应按渠道、persona 做离线回测，再调整权重，而不是凭感觉改阈值。

**怎样抑制误投？**

先用学生、毕业届、实习性质、地点、出勤和时长做 blocker；任何 blocker 都把最终分压到 49 以下；再要求已核验证据和人工确认。这样宁可进入待复核，也不把不符合约束的岗位排到 S/A。

**怎样增强召回？**

补充真实技能同义词、维护来源可靠性、把未知字段进入待确认而不是直接拒绝，并在离线评估中观察 Recall@K、MRR 和 citation coverage。不能只把阈值调低，因为那会同时放大误匹配。

**怎样证明没有幻觉？**

输出必须有 citation；引用类型只允许 `job`、`career_evidence`、`career_chunk`；预期证据的 coverage 必须为 1，输出长度至少 20 个字符。它是一个可审计门槛，不是“模型绝对不会错”的证明。

**为什么不自动投递？**

因为投递会产生外部不可逆动作。系统将发现、分析和草稿生成自动化，把写入申请状态、邮件和真实平台投递放在人工审批边界内。

## 诚实边界

- 该项目可以证明排序、证据引用、队列和审批边界；不能把代码中的演示 fixture 或本地 smoke test 说成真实招聘转化率。
- 不能声称已经接管 BOSS、领英或其他平台的自动投递；真实平台的登录、验证码和最终发送仍在系统外部。
- 面试中把“已实现参数”和“下一步可回测的参数”分开说，比堆砌模型名称更可信。
